The full CLI reference, the raw `dotnet new` route, and how to change the template itself.

To install the CLI and get a project running, start with link:install.adoc[Installation].

toc::[]

== How the pieces fit together

[listing]
----
   dotnet-api-template            a .NET global tool (tools/DotnetApiTemplate.Cli)
        │                         installed by scripts/install.sh or install.ps1
        │
        ├── carries ────────────▶ the template payload: this whole repository,
        │                         minus tools/, scripts/ and build output
        │
        ├── registers ──────────▶ `dotnet new cleanapi`  (once per tool version)
        │
        └── on `new` ───────────▶ validates the name
                                  runs dotnet new with the mapped arguments
                                  writes .env with real secrets
                                  git init + first commit
----

The template travels *inside* the tool. There is no separate template package, and no way for the
two to drift out of step — the template only changes when you reinstall the tool.

== CLI reference

=== `new`

[source,bash]
----
dotnet-api-template new --project-name <name> [options]
dotnet-api-template new <name> [options]            # the name may be positional
----

[cols="2,1,1,3", options="header"]
|===
| Option | Alias | Default | Effect

| `--project-name`
| `-n` | _required_
| The solution name, every project name, every assembly name and every root namespace.
  Must be a valid dotted C# identifier chain.

| `--output`
| `-o` | current directory
| Parent directory. The project is created in `<output>/<project-name>`.

| `--allow-grpc`
| `-g` | off
| Adds `Grpc.AspNetCore`, `Protos/users.proto` and `UsersGrpcService`, and maps the service plus
  reflection in Development. When off, those files and package references are removed entirely
  rather than left behind disabled.

| `--kafka-topic-prefix`
| `-k` | lower-cased project name
| Prefix for every topic, the consumer group id and the Redis key namespace.
  `Acme.Billing` gives `acme-billing`, so topics become `acme-billing.user.invited`.

| `--api-port`
| `-p` | `5080`
| Host port Compose publishes the API on, and the URL in `launchSettings.json`.

| `--database-name`
| `-d` | `appdb`
| PostgreSQL database name in `.env.sample`, `compose.yml` and the design-time factory fallback.

| `--no-tests`  | | off | Omit the three test projects and their solution folder.
| `--no-docs`   | | off | Omit `docs/`.
| `--no-env`    | | off | Do not write `.env`. You then have to copy `.env.sample` and set the secrets yourself.
| `--no-git`    | | off | Do not run `git init` and the first commit.
| `--no-restore`| | off | Skip the automatic `dotnet restore`.
| `--force`     | | off | Overwrite a non-empty output directory.
| `--dry-run`   | | off | Print the `dotnet new` command that would run, and write nothing.
| `--help`      | `-h` | | Show the options.
|===

Examples:

[source,bash]
----
dotnet-api-template new --project-name Acme.Billing
dotnet-api-template new Acme.Billing --allow-grpc -k billing
dotnet-api-template new -n Contoso.Orders -o ~/src -p 6000 -d ordersdb
dotnet-api-template new -n Acme.Billing --dry-run
----

=== Other commands

[cols="2,3", options="header"]
|===
| Command | Does

| `dotnet-api-template info`
| Version, where the bundled template lives, and whether the SDK, Docker and git are present.
  Aliased as `doctor`.

| `dotnet-api-template update`
| Re-registers the bundled template with the SDK. Fixes the case where the SDK's template cache
  and the tool disagree. It does *not* fetch a newer template — reinstall the tool for that.

| `dotnet-api-template uninstall-template`
| Unregisters the template, leaving the tool installed.

| `dotnet-api-template version`
| Prints the version.
|===

Exit codes: `0` success, `64` usage error, `70` generation failed, `130` cancelled.

== What the project name changes

This is the point of the whole exercise, so it is worth being concrete. With
`--project-name Acme.Billing`:

[cols="2,3", options="header"]
|===
| Where | Becomes

| Solution              | `Acme.Billing.slnx`
| Project directories   | `src/Acme.Billing.Domain/`, `src/Acme.Billing.Api/`, …
| Project files         | `Acme.Billing.Domain.csproj`, …
| Assembly names        | `Acme.Billing.Domain`, `Acme.Billing.Api`, …
| Root namespaces       | `Acme.Billing.Domain`, `Acme.Billing.Api`, …
| Namespace declarations| `namespace Acme.Billing.Application.Users.Commands;`
| Using directives      | `using Acme.Billing.Domain.Users;`
| Test projects         | `tests/Acme.Billing.Domain.UnitTests/`
| Docker image names    | derived from the Compose project name
| gRPC namespace        | `option csharp_namespace = "Acme.Billing.Api.Grpc";`
|===

Nothing is left carrying the template's own name. You can check:

[source,bash]
----
grep -rIn "CleanArchTemplate" Acme.Billing --exclude-dir=obj --exclude-dir=bin   # no matches
----

The Kafka topic prefix is a *separate* value, because the two are not the same concern: the
project name is a code identity, the prefix is a deployment identity you may well want to override
per environment. It defaults to a lower-cased form of the project name so you rarely have to think
about it.

== The raw `dotnet new` route

The CLI is a convenience over `dotnet new`. If you would rather not install a global tool, or you
are scripting in CI, use the template package directly.

[source,bash]
----
dotnet new install ProfmcdanDotnetApiTemplate.Templates
dotnet new cleanapi -n Acme.Billing --allow-grpc --kafka-topic-prefix billing
----

Or from a clone, which is what you want while changing the template:

[source,bash,subs="attributes"]
----
git clone {repo}.git
dotnet new install ./dotnet-api-template
----

[cols="2,1,3", options="header"]
|===
| `dotnet new` parameter | Alias | CLI equivalent

| `-n, --name`           |      | `--project-name`
| `--allow-grpc`         | `-g` | `--allow-grpc`
| `--kafka-topic-prefix` | `-k` | `--kafka-topic-prefix`
| `--api-port`           | `-p` | `--api-port`
| `--database-name`      | `-d` | `--database-name`
| `--include-tests`      | `-t` | `--no-tests` (inverted)
| `--include-docs`       |      | `--no-docs` (inverted)
| `--skip-restore`       |      | `--no-restore`
|===

[NOTE]
====
`dotnet new` uses the SDK's built-in `-n/--name`, which cannot be renamed by a template. That is
why `--project-name` exists on the CLI and not on the raw template — the CLI maps one to the other.
`dotnet-api-template new --dry-run` prints the exact command it would run.
====

What you give up by going this way: name validation with a readable message, the generated
`.env` secrets, and the initial commit.

== After generating

[cols="1,4", options="header"]
|===
| | Step

| 1
| Set `MIGRATOR__SEEDADMINEMAIL` and `MIGRATOR__SEEDADMINPASSWORD` in `.env` — still the sample
  values. The signing key and database password were generated for you.

| 2
| Set `APP__PUBLICBASEURL` to your front end. Every link in every email is built from it.

| 3
| `docker compose up -d`, then confirm the invite flow through Mailpit at http://localhost:8025.

| 4
| `dotnet test` — all three projects should be green before you write any of your own code.

| 5
| Replace the sample domain with yours. `User` and `Invitation` are meant to stay; they are the
  user-management feature, not a demo.

| 6
| Rename `EMAIL__FROMDISPLAYNAME`, `APP__SUPPORTURL` and the templates under
  `Infrastructure/Notifications/Templates`.
|===

Before the first real deployment, work through the
link:../README.adoc#_before_you_ship[Before you ship] checklist.

== Changing the template

The template is this repository. Edit the code, reinstall the tool, and the next generated project
has your change.

[source,bash]
----
./scripts/install.sh          # rebuild the tool with your edited template inside it
----

Things worth knowing before you edit `.template.config/template.json`:

* *`sourceName` is `CleanArchTemplate`.* Every occurrence, in file names and file contents, is
  replaced with the project name. Do not use that string for anything you do not want renamed.
* *Symbol replacement is literal.* `KafkaTopicPrefix` replaces the exact lowercase string
  `cleanarch`. That is why the Compose services are named `postgres` and `redis` rather than
  `cleanarch-postgres` — so changing the prefix does not rename containers as a side effect.
* *Conditional blocks use the file's comment syntax.* `//#if (AllowGrpc)` … `//#endif` in C#;
  `<!--#if (AllowGrpc) -->` … `<!--#endif -->` in `.csproj`, `.props` and `.slnx`.
* *Whole files are excluded with `sources[0].modifiers`,* not with conditionals. That is how the
  `Grpc/` and `Protos/` folders disappear.
* *`tools/`, `scripts/` and `artifacts/` are excluded from the payload,* so generated projects do
  not carry the CLI around with them.

=== Testing a template change

Always exercise both sides of a boolean:

[source,bash]
----
./scripts/install.sh
cd "$(mktemp -d)"

dotnet-api-template new -n WithGrpc --allow-grpc && dotnet build WithGrpc/WithGrpc.slnx
dotnet-api-template new -n Plain                 && dotnet build Plain/Plain.slnx
dotnet-api-template new -n Minimal --no-tests --no-docs && dotnet build Minimal/Minimal.slnx
----

Then grep for leftovers — a missed `#endif` or an unreplaced token shows up immediately:

[source,bash]
----
grep -rIn "CleanArchTemplate\|cleanarch" Plain --exclude-dir=obj --exclude-dir=bin
----

The CLI has its own tests for the parts that are easy to break silently — name validation and the
`.env` rewriting:

[source,bash]
----
dotnet test tools/DotnetApiTemplate.slnx
----

== Publishing to NuGet

Publishing means users install with one command and never clone anything:

[source,bash]
----
dotnet tool install --global ProfmcdanDotnetApiTemplate.Cli
dotnet-api-template new --project-name Acme.Billing
----

=== The two packages

[cols="2,1,3", options="header"]
|===
| Package | Type | Installed with

| `ProfmcdanDotnetApiTemplate.Cli`
| Global tool
| `dotnet tool install --global ProfmcdanDotnetApiTemplate.Cli`

| `ProfmcdanDotnetApiTemplate.Templates`
| Template
| `dotnet new install ProfmcdanDotnetApiTemplate.Templates`
|===

Both carry the same template payload, defined once in `Directory.Packaging.props` so they cannot
disagree, and both are versioned together. Publish both: the tool is the better experience, the
template package is there for anyone who cannot or would rather not install a global tool.

The ids carry an owner prefix because nuget.org ids are global, first-come and permanent. The
projects, namespaces and the `dotnet-api-template` command itself keep the shorter name — the
prefix exists to make the *published* id unmistakably yours, not to make the code noisier.
`PackageIdPrefix` in `Directory.Packaging.props` is the single place it is set.

[TIP]
====
If you would rather reserve the prefix properly, use a dotted form such as
`Profmcdan.DotnetApiTemplate.Cli` and apply for an
https://learn.microsoft.com/nuget/nuget-org/id-prefix-reservation[ID prefix reservation] on
`Profmcdan.*`. A reservation gives you the blue verified tick and stops anyone else publishing
under that prefix; it only works with dot-separated prefixes. Change `PackageIdPrefix` and
re-run the docs commands — nothing else needs touching.
====

=== One-time setup

Publishing uses nuget.org *Trusted Publishing*: GitHub mints a short-lived, cryptographically
signed token describing this repository and workflow, nuget.org validates it against a policy you
registered, and issues an API key that expires after an hour. Nothing long-lived is stored in the
repository, so there is no key to leak, rotate or accidentally scope wrongly.

[IMPORTANT]
====
Do this *before* your first tag. Without it the release workflow stops at its first step —
nothing is published, but the tag is already out there.
====

==== 1. Register the policy on nuget.org

Sign in, click your username, choose *Trusted Publishing*, and add a policy:

[cols="1,3", options="header"]
|===
| Field | Value

| Policy name      | Anything memorable, e.g. `dotnet-api-template`
| Owner            | You, or an organisation you are an active member of
| Repository Owner | `profmcdan`
| Repository       | `dotnet-api-template`
| Workflow File    | `release.yml` — the *file name only*, not `.github/workflows/release.yml`
| Environment      | Leave empty, unless you add a GitHub environment (see below)
|===

The policy is scoped to the *owner*, not to a package, so it covers ids that do not exist yet —
which is what you need for a first publish.

[NOTE]
====
Trusted Publishing is being rolled out gradually. If the option is not in your account menu yet,
see <<If Trusted Publishing is not available yet>>.
====

==== 2. Tell the workflow who to publish as

Add a repository *variable* named `NUGET_USER`, set to your nuget.org profile name — *not* your
email address. Settings → Secrets and variables → Actions → *Variables*.

It is an identifier rather than a credential, which is why it is a variable. The workflow also
accepts it as a secret if you prefer, which is what the Microsoft documentation suggests.

==== 3. Rehearse it

Run the workflow from the Actions tab with `workflow_dispatch` and `dry_run: true`. That tests,
packs, installs the packed tool and scaffolds a project with it, then uploads the packages as
build artifacts *without* touching nuget.org.

[CAUTION]
====
A dry run skips the token exchange, so it does not prove the policy is right. The first real
release is what validates that — which is why the preflight step and the failure summaries exist.
====

==== Private repositories: the seven-day window

A policy for a private repository starts *temporarily active* for seven days. nuget.org needs the
numeric GitHub repository and owner ids to pin the policy, and it only receives those from a real
publish — that is what stops someone deleting a repository, recreating it under the same name and
inheriting your publishing rights.

Publish once inside that window and the policy becomes permanently active. Miss it and the policy
goes inactive; you can restart the window from the UI at any time.

==== Optional: gate releases behind an environment

For tighter control, add `environment: release` to the `publish` job, create that environment in
Settings → Environments with required reviewers, and set *Environment* to `release` on the
nuget.org policy. A release then needs a human approval before the token is ever minted.

==== If Trusted Publishing is not available yet

Fall back to an API key until it appears in your account. Create one at
https://www.nuget.org/account/apikeys with glob pattern `ProfmcdanDotnetApiTemplate.*` and the
"Push new packages and package versions" scope, add it as a repository secret `NUGET_API_KEY`, and
in `.github/workflows/release.yml` drop the `NuGet/login` step and change the push step's
environment to:

[source,yaml]
----
        env:
          NUGET_API_KEY: ${{ secrets.NUGET_API_KEY }}
----

Switch back as soon as you can. A long-lived key is the thing Trusted Publishing exists to remove.

=== Releasing

One command bumps the version, runs the tests, commits and tags:

[source,bash]
----
./scripts/release.sh 1.1.0
----

It refuses to run on a dirty tree or an existing tag, and it does *not* push — publishing to
nuget.org is permanent, so review first:

[source,bash]
----
git show --stat HEAD
git push origin HEAD --follow-tags
----

Add `--push` to do both in one step once you trust it.

[IMPORTANT]
====
Bump the version with the script rather than by hand. The release workflow refuses to publish when
the tag and the checked-in version disagree, and doing it in three manual steps is exactly how they
come to disagree.
====

Pushing the tag triggers `.github/workflows/release.yml`, which:

. Checks the tag matches the version the projects actually evaluate to — read from MSBuild, not
  scraped out of the XML, so a `Version` mentioned in a comment cannot fool it.
. Runs the full test suite, application and tooling.
. Packs both packages with the version from the tag.
. *Installs the packed tool and scaffolds a project with it*, so a broken package cannot reach
  nuget.org.
. Exchanges a GitHub OIDC token for a one-hour nuget.org key, immediately before pushing.
. Pushes to nuget.org with `--skip-duplicate`.
. Opens a GitHub release with the packages attached and install instructions in the body.

==== From Windows, or without the script

The `workflow_dispatch` trigger runs the same job from the GitHub Actions UI, with a `dry_run`
option that packs and uploads the artifacts without pushing to nuget.org. Worth using once before
your first real release.

By hand, the sequence is:

[source,bash]
----
# 1. edit the Version property in Directory.Packaging.props
git commit -am "chore: release 1.1.0"
git tag -a v1.1.0 -m "Release 1.1.0"
git push origin HEAD --follow-tags
----

==== Recovering from a mismatched tag

If the workflow fails with a version mismatch, the tag was pushed without the matching bump.
Delete it and cut the release properly — nothing was published, so this is safe:

[source,bash]
----
git tag -d v1.1.0
git push --delete origin v1.1.0

./scripts/release.sh 1.1.0
git push origin HEAD --follow-tags
----

=== Publishing by hand

Trusted Publishing only works from CI — the token comes from GitHub, so there is nothing to
exchange on a laptop. Prefer the `workflow_dispatch` trigger if you want to release outside the
tag flow.

If you must push locally, create a temporary API key on nuget.org, use it, then revoke it:

[source,bash]
----
dotnet test CleanArchTemplate.slnx
dotnet test tools/DotnetApiTemplate.slnx

dotnet pack tools/DotnetApiTemplate.slnx -c Release -o ./artifacts -p:Version=1.1.0

# Try it before pushing - installing from a local folder is the same code path as nuget.org.
dotnet tool install --global --add-source "$PWD/artifacts" ProfmcdanDotnetApiTemplate.Cli --version 1.1.0
dotnet-api-template new --project-name Smoke.Test --no-git && dotnet build Smoke.Test/Smoke.Test.slnx

dotnet nuget push "artifacts/*.nupkg" \
  --source https://api.nuget.org/v3/index.json \
  --api-key "$NUGET_API_KEY" \
  --skip-duplicate
----

`--add-source` needs an absolute path; a relative one is silently skipped with a warning.

=== A private feed instead

Same commands, different source — GitHub Packages, Azure Artifacts and a plain folder on a share
all work:

[source,bash]
----
dotnet nuget push "artifacts/*.nupkg" --source <feed-url> --api-key <key>
dotnet tool install --global ProfmcdanDotnetApiTemplate.Cli --add-source <feed-url>
----

=== Versioning

The tool version *is* the template version, because the template ships inside the package. That is
the useful property: `--version 1.2.0` pins an exact scaffold, so everyone on a team generates
identical projects.

[cols="1,3", options="header"]
|===
| Bump | When

| Patch
| A fix inside the generated code or the CLI that does not change the shape of a new project.

| Minor
| New capability in the template, or a new CLI option. Existing projects are unaffected — they
  were copied, not linked.

| Major
| A change that would surprise someone expecting the previous scaffold: a renamed layer, a
  different messaging contract, a dropped option.
|===

Pre-release versions work as usual and are a good way to try a scaffold before committing to it:

[source,bash]
----
git tag v1.2.0-rc.1
dotnet tool install --global ProfmcdanDotnetApiTemplate.Cli --version 1.2.0-rc.1
----

[IMPORTANT]
====
`NoDefaultExcludes` is set in `Directory.Packaging.props` so dot-prefixed paths survive packing.
Without it NuGet silently drops `.template.config/`, `.gitignore`, `.editorconfig` and
`.env.sample` — and the published package produces broken projects. Do not remove it.
====

== Troubleshooting

[cols="2,3", options="header"]
|===
| Symptom | Cause and fix

| Changes to the template do not appear in new projects
| The tool bundles the template. Re-run `./scripts/install.sh`.

| Changes to `template.json` have no effect
| The SDK caches the manifest. `dotnet-api-template update`, or
  `dotnet new install <path> --force`.

| Generated project still contains `CleanArchTemplate`
| A file type the engine does not treat as text, or a path in the `exclude` list of
  `sources[0]`.

| `bin/` and `obj/` end up in the generated project
| You installed the template from a built repository. The payload glob and the template's own
  exclude list both cover `**/bin/**` and `**/obj/**`; run `git clean -xdn` to see what else is
  lying around.

| gRPC files remain with `--allow-grpc` off
| The `modifiers` condition and the folder path must match exactly, and exclusion is evaluated
  against the *template's* names — keep the pattern on `src/CleanArchTemplate.Api/…`.

| `dotnet pack` fails with NU5119
| A dot-prefixed file is being excluded. `NoDefaultExcludes` should be `true` in
  `Directory.Packaging.props`.

| The release workflow fails on the version check
| The tag was pushed without the matching version bump. See
  <<Recovering from a mismatched tag>>. Using `./scripts/release.sh` avoids it entirely.

| No *Trusted Publishing* option in the nuget.org account menu
| Still rolling out. Use <<If Trusted Publishing is not available yet>> in the meantime.

| The `NuGet/login` step fails to exchange the token
| The token did not match a policy. Every field is compared: Repository Owner, Repository, and
  Workflow File — which is `release.yml`, the file name alone, with no `.github/workflows/`
  prefix. If the policy sets an Environment, the job must declare the same one.

| `Unable to get ACTIONS_ID_TOKEN_REQUEST_URL`
| The job cannot mint an OIDC token. `permissions: id-token: write` must be present, and a
  workflow triggered from a fork will not get one.

| The policy shows as inactive
| Either the seven-day window for a private repository lapsed before the first publish — restart
  it from the UI — or the policy is owned by an organisation you are no longer a member of.

| `dotnet nuget push` returns 403
| The key was issued, so the policy matched, but the policy owner does not own that package id.
  Ids are first-come and permanent; check nobody else has taken it.

| `dotnet nuget push` returns 409
| That version already exists on nuget.org. Versions are immutable: bump and re-tag. The workflow
  passes `--skip-duplicate`, so this only surfaces when pushing by hand.

| `dotnet nuget push` returns 401 after the key was issued
| The key expired — it lasts one hour. Re-run the job from the start rather than resuming it.

| `--add-source ./artifacts` is ignored with "the source is not valid"
| NuGet needs an absolute path there. Use `"$PWD/artifacts"`.

| A published version has a mistake in it
| Versions cannot be replaced or deleted, only unlisted. Unlist it on nuget.org and publish a
  patch.

| Restore fails immediately after generating
| Usually an offline feed or a private source in a parent-directory `NuGet.config`. Generate with
  `--no-restore` and run `dotnet restore` yourself to see the real error.
|===
