= CleanArchTemplate
:toc: macro
:toclevels: 3
:icons: font
:source-highlighter: rouge
:experimental:
:repo: https://github.com/profmcdan/dotnet-api-template

A production-shaped ASP.NET Core Web API template: clean architecture, JWT user management with
an invite-by-email flow carried over Kafka, a transactional outbox, EF Core on PostgreSQL, Redis,
a migrator job, background workers, and a Docker Compose stack that runs the whole thing.

It ships as a CLI on NuGet:

[source,bash]
----
dotnet tool install --global ProfmcdanDotnetApiTemplate.Cli
dotnet-api-template new --project-name Acme.Billing --allow-grpc
----

That renames everything to your project — solution, projects, assemblies and namespaces — writes
a `.env` with real generated secrets, and makes the first commit. `docker compose up` then gives
you a working system with a seeded administrator, created Kafka topics and a local mail catcher.

toc::[]

== What you get

[cols="1,3", options="header"]
|===
| Area | What is already built

| Architecture
| Four layers with a one-way dependency rule, enforced by project references. Domain has no
  dependencies at all.

| CQRS
| A small hand-rolled dispatcher with logging, validation and transaction behaviours.
  *No MediatR* - no licence to worry about, and about 60 lines you can actually read.

| Persistence
| EF Core 10 on PostgreSQL 18. Explicit column mappings, partial unique indexes, `timestamptz`
  everywhere, soft delete, audit columns applied by an interceptor.

| User management
| Invite → accept → sign in. Roles, suspension and reinstatement, self-service profile and
  password change.

| Authentication
| Short-lived JWT access tokens plus rotating refresh tokens with reuse detection, and a security
  stamp so suspension takes effect immediately rather than whenever the token expires.

| Messaging
| Kafka (Redpanda locally) with a transactional outbox, a configurable topic prefix, explicit
  topic provisioning, manual offset commits, bounded retries and a dead-letter topic.

| Email
| HTML and plain-text templates with an action callout button, rendered from embedded resources
  and delivered by a dedicated worker. Idempotency keys stop duplicate sends.

| Operations
| Multi-stage non-root Dockerfile, read-only root filesystem, liveness and readiness probes,
  Serilog, OpenTelemetry traces and metrics, a run-to-completion migrator job.

| Tests
| Domain and application unit tests, plus integration tests that run against real PostgreSQL,
  Redis and Redpanda containers via Testcontainers.

| Tooling
| A `dotnet-api-template` global tool that bundles the template, validates the project name,
  generates the secrets and initialises git — with its own test suite.
|===

== Quick start

[source,bash]
----
dotnet tool install --global ProfmcdanDotnetApiTemplate.Cli

dotnet-api-template new --project-name Acme.Billing --allow-grpc
cd Acme.Billing
docker compose up -d
----

The project name is applied across the board — the solution, every project, every assembly and
every namespace become `Acme.Billing.*`. The CLI also writes `.env` with a freshly generated
signing key and database password, and makes the first commit.

Prefer no global tool? The template is published on its own too:

[source,bash]
----
dotnet new install ProfmcdanDotnetApiTemplate.Templates
dotnet new cleanapi -n Acme.Billing --allow-grpc
----

Working on the template itself, or before the first release is published — build the CLI from
source:

[source,bash,subs="attributes"]
----
git clone {repo}.git
cd dotnet-api-template
./scripts/install.sh          # .\scripts\install.ps1 on Windows
----

`docker compose up` builds three images and starts seven containers. The migrator applies the
schema, creates the Kafka topics and seeds the bootstrap administrator, then the API and worker
start.

[cols="2,3,3", options="header"]
|===
| Service | URL | Notes

| API | http://localhost:5080 | REST surface
| API reference | http://localhost:5080/scalar/v1 | Development only
| Health | http://localhost:5080/health/ready | `live` and `ready` are separate
| Redpanda Console | http://localhost:8085 | Browse topics and messages
| Mailpit | http://localhost:8025 | Every outbound email lands here
| Postgres | localhost:5432 | Credentials from `.env`
| Redis | localhost:6379 |
|===

Try the invite flow end to end:

[source,bash]
----
# 1. sign in as the seeded administrator
TOKEN=$(curl -s -X POST http://localhost:5080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@example.com","password":"change-me-immediately-1"}' \
  | jq -r .accessToken)

# 2. invite someone
curl -s -X POST http://localhost:5080/api/v1/users/invitations \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"email":"ada@example.com","fullName":"Ada Lovelace","roles":["member"]}'

# 3. open http://localhost:8025 and click the invitation link
----

Behind those two calls: the API wrote a user, an invitation and an outbox row in one transaction;
the outbox processor published to `<prefix>.user.invited`; a consumer turned that into
`<prefix>.email.requested`; and the email worker rendered the template and sent it.

== How a request travels

[listing]
----
  HTTP                Application                         Infrastructure
  ────                ───────────                         ──────────────
  Controller
     │  ISender.SendAsync(command)
     ▼
  LoggingBehavior ──▶ ValidationBehavior ──▶ TransactionBehavior
                                                   │
                                                   ▼
                                          Command handler
                                             │        │
                        repository interfaces│        │domain aggregate
                                             ▼        ▼
                                     EF Core repo   User / Invitation
                                             │        │ raises domain events
                                             ▼        ▼
                                     SaveChangesAsync ── interceptor ──▶ outbox row
                                             │                            (same transaction)
                                             ▼
                                         PostgreSQL
----

The controller never touches a `DbContext`, a repository or a query. It depends on `ISender` and
nothing else, which is what keeps the HTTP layer swappable and the handlers testable without a
web host.

== CLI options

[source,bash]
----
dotnet-api-template new --help
----

[cols="2,1,1,3", options="header"]
|===
| Option | Alias | Default | Effect

| `--project-name`       | `-n` | _required_  | Solution, project, assembly and namespace names.
| `--output`             | `-o` | current dir | Parent directory for the new project.
| `--allow-grpc`         | `-g` | off         | Adds a gRPC surface over the same query handlers.
| `--kafka-topic-prefix` | `-k` | from name   | Topic prefix, consumer group and Redis key namespace.
| `--api-port`           | `-p` | `5080`      | Host port Compose publishes the API on.
| `--database-name`      | `-d` | `appdb`     | PostgreSQL database name.
| `--no-tests`           |      | off         | Omit the test projects.
| `--no-docs`            |      | off         | Omit `docs/`.
| `--no-env`             |      | off         | Do not write `.env` with generated secrets.
| `--no-git`             |      | off         | Do not `git init` and commit.
| `--dry-run`            |      | off         | Print the command that would run; write nothing.
|===

Other commands: `info` (version and prerequisite check), `update` (re-register the template),
`uninstall-template`, `version`.

Prefer not to install a tool? The template also works directly:

[source,bash]
----
dotnet new install .
dotnet new cleanapi -n Acme.Billing --allow-grpc --kafka-topic-prefix billing
----

See link:docs/template-usage.adoc[template usage] for the full reference and the differences
between the two routes.

== Common tasks

[source,bash]
----
# build and test the application
dotnet build CleanArchTemplate.slnx
dotnet test CleanArchTemplate.slnx

# build and test the CLI itself
dotnet test tools/DotnetApiTemplate.slnx

# rebuild and reinstall the CLI after changing the template
./scripts/install.sh

# pack both NuGet packages locally
dotnet pack tools/DotnetApiTemplate.slnx -c Release -o ./artifacts

# unit tests only (no Docker required)
dotnet test tests/CleanArchTemplate.Domain.UnitTests
dotnet test tests/CleanArchTemplate.Application.UnitTests

# add a migration (Infrastructure holds them, Migrator is the startup project)
dotnet dotnet-ef migrations add AddThing \
  --project src/CleanArchTemplate.Infrastructure \
  --startup-project src/CleanArchTemplate.Migrator \
  --output-dir Persistence/Migrations

# re-run only the topic seeding step
docker compose run --rm migrator kafka-topics

# follow the worker
docker compose logs -f worker

# stop everything, keeping data
docker compose down

# stop everything and delete the volumes
docker compose down -v
----

== Releasing this template

[source,bash]
----
./scripts/release.sh 1.1.0        # bump, test, commit, tag
git push origin HEAD --follow-tags
----

Pushing the tag runs `.github/workflows/release.yml`, which tests, packs both packages, installs
the packed tool and scaffolds a project with it, then pushes to nuget.org and opens a GitHub
release. It needs one repository secret, `NUGET_API_KEY`.

Bump with the script rather than by hand — the workflow refuses to publish when the tag and the
checked-in version disagree.

Full details, including publishing by hand, releasing from Windows and recovering from a
mismatched tag, are in link:docs/template-usage.adoc#_publishing_to_nuget[template usage].

== Before you ship

* Replace `JWT__SIGNINGKEY` with a real secret (`openssl rand -base64 48`) held in a secret store,
  not in `.env`.
* Change `POSTGRES_PASSWORD` and remove `MIGRATOR__SEEDADMINEMAIL` / `MIGRATOR__SEEDADMINPASSWORD`
  once a real administrator exists.
* Point `APP__PUBLICBASEURL` at your real front end - every link in every email is built from it.
* Put a shared rate limiter at the edge. The built-in limiter is per instance.
* Set `KAFKA__DEFAULTREPLICATIONFACTOR` to at least `3` on a real cluster.
* Review link:docs/architecture.adoc#_failure_modes[failure modes] and decide which alerts you want.
